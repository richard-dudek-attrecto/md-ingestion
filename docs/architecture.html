Multi-Device Data Ingestion Prototype — Architecture

Spring Boot (Java 21) service that ingests telemetry from heterogeneous devices, normalizes each device-specific payload into one common model, classifies late / out-of-order data, and publishes the normalized stream to a downstream sink.

1. System model

⚠ Note — the inspection layer is testing only.

The TelemetryInspectionService and TelemetryInspectionController (endpoints GET /api/v1/events and /api/v1/events/late) exist solely to visualize the in-memory buffer from the browser test console. They are not part of the production downstream contract. In a real deployment nothing "reads back" from the pipeline over HTTP — a downstream system consumes the events from the sink (see section 4).

2. Request flow

  1. A device posts a raw payload to IngestionController (/ingest/temperature or /ingest/vibration).
  2. IngestionService resolves the matching DeviceIngestionStrategy via the IngestionStrategyRegistry and normalizes the payload into one or more NormalizedTelemetryEvents. Bursty payloads fan out to one event per sample.
  3. WatermarkLateArrivalPolicy classifies each event against the per-device watermark.
  4. Each classified event is handed to TelemetrySink.publish() — the downstream boundary.
  5. The in-memory sink forwards events to InMemoryTelemetryStore. The testing-only inspection layer reads that store for visualization.

3. Lateness / out-of-order handling

Each device keeps its own watermark = the highest event timestamp seen so far (monotonic, never decreases). Every incoming event is compared to it:

ConditionClassification
timestamp ≥ watermark (equal counts as on-time)ON_TIME
timestamp < watermark, within ingestion.allowed-latenessOUT_OF_ORDER
older than the allowed-lateness windowLATE

The classification is stamped onto the event (isLate + metrics.lateness) so it travels with the data. Tolerance is configurable via ingestion.allowed-lateness (default PT30S).

Known nuance: because a vibration burst is currently fanned out into per-sample timestamps (recordedAt + index·100ms) and the watermark advances per sample, re-sending the same burst flags earlier samples as OUT_OF_ORDER while the last one stays ON_TIME. Evaluating lateness per burst instead of per sample is a natural refinement (see next section).

4. Suggested next steps for developers

Replace the in-memory sink with a real downstream highest impact

The whole point of the TelemetrySink interface is that the destination is swappable without touching the controller, strategies, or policy. Provide a new implementation and delete/deactivate the in-memory one:

  • Relational DB (JPA): a JpaTelemetrySink that persists each NormalizedTelemetryEvent to Postgres/MySQL. Good for querying and audit.
  • Apache Kafka: a KafkaTelemetrySink using KafkaTemplate to publish to a topic (e.g. keyed by deviceId for ordering). Best fit for high-throughput streaming and multiple independent consumers.
  • RabbitMQ / JMS: a RabbitTelemetrySink for classic message-queue fan-out and work-queue semantics.
  • Cloud streams: AWS Kinesis / managed Kafka via the same pattern.

Route LATE events to a dedicated topic / dead-letter queue / table so they can be reprocessed or audited separately.

Retire the inspection layer for production

Once a real sink is in place, remove or guard the inspection package behind a Spring profile (e.g. @Profile("dev")) so the visualization endpoints never ship to production.

Other refinements

  • Per-burst lateness: classify a vibration burst once against recordedAt and stamp all its samples equally (fixes the per-sample nuance above).
  • Bounded buffers / back-pressure: the in-memory store is unbounded; a production sink needs bounding, batching, or async publishing.
  • Idempotency & dedup: use eventId / a natural key to drop duplicates on re-send.
  • Reordering window: add a buffered, time-windowed re-sort for out-of-order events before downstream delivery if consumers require ordering.
  • Observability: Micrometer metrics (counts per DeviceType / lateness), structured logging, tracing.
  • Schema & versioning: version the DTOs and the normalized model for evolving devices.
  • Persistence of watermarks: currently in-process; externalize (Redis/DB) for multi-instance deployments.

5. Extensibility — adding a new device type

No changes to existing code (Open-Closed):

  1. Add a value to DeviceType.
  2. Add a DTO in the dto package.
  3. Implement DeviceIngestionStrategy<NewDto> as a @Component.

Spring injects the new strategy into IngestionStrategyRegistry automatically.
